This report covers why that is the most important thing to fix in this product, how I found it, the options I weighed, and the change I made across the API and the web app.

SummaryOne defect, four layers, and the person it hurts most never sees it

The product exists to produce one thing: a skill rating an assessor can defend. I found that the pipeline producing that rating fabricates certainty. If an interview ends before a skill is discussed (the candidate's connection drops, or they press "End interview", which the product tells them they can do at any time), that skill is stored as L1, and the fit/gap report calls it a gap.

Why this, first

It is a silent false low: a qualified candidate is rejected for a skill nobody asked about, and nobody re-checks a rejection.

Why it matters commercially

"Errors caused by AI" and "risk of bias" are top reasons Indonesian companies don't use AI in hiring. One visible fabricated rating confirms both.

Why it's verifiable

The pipeline starts from a model response, so every case can be tested with a stubbed model. No live calls, no flaky tests.

Step 2 · Domain immersionWhat does it take for a rating to be worth trusting?

An assessor configures the skills a role needs and what each level (L1–L5) looks like. The candidate opens a link and talks to an AI interviewer that probes their answers. A coverage map (not_yet → initiated → partial → covered) steers the next question. After the session, a model writes a skill portfolio (level, confidence, evidence quotes, summary), and a fit/gap report compares it with a vacancy. I asked one question from five angles.

Blue: where trust is won or lost. Everyone downstream acts on the portfolio, not on the interview.

1 · The product, used end to end

The center of gravity is the result review, not the interview. The interview impresses; the portfolio and fit/gap are what someone acts on. Also found: the candidate page is English only even for a Bahasa Indonesia interview, and the interviewer is told never to switch language, though mixing Indonesian and English is normal in Indonesian tech workplaces.

2 · The industry

In a Jobstreet by SEEK survey of 1,273 HR practitioners (2024), 80% of Indonesian companies don't use AI in recruitment. Top reasons: no human touch (44%), cost (40%), risk of bias (38%), AI errors (27%). The product sells into skepticism; its weakest point is exactly the one buyers fear.

3 · What it's for

Give a hiring team a level per skill they can defend, without spending an engineer's hour on every first-round candidate. The two errors aren't symmetric: a false high costs one more interview; a false low is silent. The output must stay decision support, never auto-reject.

4 · The users who act on it

The assessor needs to tell measured-low from never-measured. The recruiter needs to see what's waiting. The hiring manager needs real gaps vs unknowns, and what to probe next. Today one admin role does all three jobs, and the override only works if the assessor knows when to doubt the AI.

5 · The candidate who never chose this

The candidate can't see the output and usually can't refuse without losing the opportunity. The page says "You can end anytime", and ending early silently turns every skill not yet reached into L1. They're penalized for using an option the product offered, and never told. In Indonesia, a dropped mobile connection does the same.

Step 4 · StrategyMake "not assessed" a real state, end to end

A skill the interview never reached, or that the model couldn't rate, is stored with no level and a reason. It reaches fit/gap as not assessed, not as a gap. The assessor sees a neutral state that says why, and can add a rating. Along the way the write becomes atomic, keeps overrides, accounts for every configured skill, and drops quotes that aren't in the transcript.

Decision: B. The smallest change that makes every output honest. C's extras need product decisions (verdict thresholds; what to do with past ratings), so they're follow-ups. Past ratings are not rewritten; a read-only task reports how many are affected. The session's end reason isn't trusted either (anyone with the link can end it as "all covered", P1-10), so "assessed" is decided by the coverage map and the model output only.

Acceptance criteria (30, written before code)

Generator (AC-1 to AC-12)

null or junk levels (0, 6, "N/A", "high", []) are never clamped; the coverage map overrules a level for a skill never probed; every configured skill gets exactly one row; unverifiable quotes are dropped and confidence lowered; any failure leaves the previous portfolio intact; overrides survive regeneration; model errors are stored as a category, never raw text; 20,000-character quotes are capped.

Fit/gap, data model, API (AC-13 to AC-21)

Not assessed is its own verdict with no delta; an override on it counts and is flagged; the payload carries both expected_level and required_level during the transition; the fallback narrative counts unknowns; the migration changes no existing row and its rollback refuses to invent levels; adding a rating to an unassessed skill requires a note.

Screens (AC-22 to AC-30)

A "Not assessed" badge with the reason in plain language and "Add rating"; null is never shown as L1; a summary line ("2 of 3 skills weren't assessed"); error states with Retry instead of a spinner or a blank page; long text collapsed; stacked rows at 375px; not conveyed by color alone; reachable by keyboard.

Delivery

Umbrella PR + sub-PRs: (1) tenant scoping, (2) web tolerates a missing level, which must land before (3) data model + generator, (4) fit/gap engine + payload, (5) portfolio and fit/gap screens. Each sub-PR flips its pinned known-defect tests to passing.

Step 4 · DesignWho decides "assessed", and the order it ships in

One place decides, the generator, and every reader (fit/gap, API, screens, PDF) only displays the result. The coverage map is checked first: a rating with zero probes has no evidence by definition, whatever the model says. The model is called before the transaction opens, so a slow call never holds the database.

Unverifiable quotes are dropped one by one. Any failure rolls back and leaves the previous portfolio intact.

AI verificationWhere the AI was wrong, and how it was caught

I used an AI assistant throughout. Every claim it made about the system was checked against something observable: a log, a real request, a failure message. Eight moments are logged in the work log; these are the ones that mattered most.

  1. A test that would have "proved" a bug for the wrong reason. Writing the tenant-isolation specs, the assistant used a factory that didn't exist. The spec was marked pending (a known defect), and pending accepts any failure, so it would have shown as proof of the cross-tenant leak while actually failing on Factory not registered. Caught by reviewing the code before the run, then reading every pending spec's failure message instead of the count. Rule now: every known-defect test is run as a normal test and must fail on its assertion.
  2. Known-defect web tests that "passed" for the wrong reason. The first web run reported the expected failures, but every render was failing with "act(...) is not supported in production builds", because the shell had NODE_ENV=production. Caught by reading the failure output, not the summary line. Fixed by pinning NODE_ENV=test.
  3. A safety check written from memory of an older library. The assistant used MSW 2's option to fail on unexpected requests; MSW 3 renamed it and silently ignores the old name, so the check was off. Caught by the type checker, then a probe test. Turning the check on immediately exposed the hardware check's calls to third-party hosts (P1-12).
  4. Retry configuration that reads right but does nothing. The model client's retry block looks careful. At runtime, the retry middleware only retries idempotent methods, and every model call is a POST (P2-3). Caught by checking the middleware's constant at runtime, not reading the config.
  5. An empty queue read as "no duplicate jobs". The queue was empty because the jobs had already run, and two had crashed (P1-6). Caught by the worker logs.
  6. "Up" doesn't mean running. Docker reported the API as up; Puma had already crashed. Caught by the logs and a real request.
